Concept · Loss function

Class-Weighted Cross-Entropy Loss

Making rarer mistakes cost more than common ones.

TL;DR

A plain cross-entropy loss treats every training example as equally important. If your classes aren't balanced, the model learns to favor the majority class — it's the cheapest way to minimize the total loss. Class weighting multiplies each example's loss by a factor inversely proportional to its class size, so the model can't win by ignoring the minority.

The problem it solves

Suppose your training set has 50 "left hand", 30 "right hand", and 10 "both hands" trials. A plain cross-entropy loss sums the loss over all 90 examples. The model can cut its total loss a lot by getting "left" right (50 samples worth of loss) while barely trying on "both" (only 10 samples worth). The shortest path to low training loss is to become a "left" specialist.

This is an optimization problem, not a data problem: the training signal is biased toward the common class because common-class errors outnumber rare-class errors. Class weighting rebalances the signal so each class contributes equally — regardless of how many samples it has.

How cross-entropy loss works (briefly)

For multi-class classification, cross-entropy is the negative log of the predicted probability for the correct class: 

loss_i = -log(softmax(logits)[y_i])       # single-sample loss

The total loss is the mean across the batch. A model that's confidently wrong gets a very high loss (log of something near zero is very negative); a model that's confidently right gets a loss near zero. The gradient points in whichever direction lowers the loss — towards being confidently right.

Adding weights

Weighted cross-entropy scales each per-sample loss by a per-class factor: 

loss_i = -w[y_i] · log(softmax(logits)[y_i])

When w[y_i] is larger for minority classes, getting a minority sample wrong costs more — the gradient becomes larger for that sample, and the optimizer responds by paying more attention to that class.

Inverse-frequency weighting

The standard way to set the weights is inverse frequency: a class with fewer samples gets a larger weight. Formula: 

w_c = 1 / count_c           # raw weight per class
w_c = w_c / sum(w_c)        # normalize so weights sum to 1

The effect: each class contributes approximately the same total loss mass across an epoch, regardless of how many samples it has.

In your project

From 04_eegnet_sweep.ipynb, cell 2: 

counts = np.bincount(y_tr, minlength=n_classes).astype(np.float32)
w = torch.tensor(1.0 / (counts + 1e-6))   # inverse frequency
w /= w.sum()                                # normalize

criterion = nn.CrossEntropyLoss(weight=w.to(DEVICE))

The + 1e-6 is a safety net: if any class ended up with zero samples in the training fold (extreme case with small datasets), you'd divide by zero without it. PyTorch's nn.CrossEntropyLoss accepts a weight tensor directly — no manual gradient manipulation needed.

Your class distribution is roughly balanced (~30 trials per class), so the weights come out nearly equal — about [0.33, 0.33, 0.33]. You don't strictly need weighting at this balance, but it's good practice:

  • Defensive: if one session ends up with fewer "both hands" trials due to noise rejection, the weights self-adjust.
  • Consistent across folds: each fold's training set has slightly different class counts (stratified, but not identical), and the weights automatically account for it.
  • Zero cost at equal counts: when classes are perfectly balanced, weighted CE is mathematically identical to unweighted CE.

Alternatives to weighting

TechniqueHowTradeoff
Class weights Multiply per-sample loss by 1/freq Cheap, easy. Your approach.
Oversampling Sample minority classes more often during training Duplicates samples — risk of overfitting to those specific ones.
Undersampling Throw away majority samples to match minority Wastes data. Usually a bad idea on small datasets.
SMOTE Synthesize new minority samples by interpolation Tricky on EEG — interpolated trials may not be physiologically valid.
Focal loss Down-weight easy samples, up-weight hard ones Popular in object detection; overkill here.

Pitfalls

Extreme imbalance + aggressive weighting can destabilize training. If one class has 1% of the data, its weight is 100× the others — a single minority example produces 100× the gradient of a majority one. You can get exploding gradients. At that point oversampling or SMOTE is often a better tool than raw weighting.

Computing weights on the full dataset instead of the training fold. The weights are a function of the training set. Inside cross-validation, compute them fresh for each fold's training subset — not the full dataset. Otherwise you're leaking validation-set information (specifically, validation-set class counts) into the training loss.

Weighting the validation loss. Use class weights during training only. Your evaluation metric (macro-F1 in your case) is what accounts for class imbalance in reporting. Weighting the reported loss/accuracy would make them harder to interpret.

Interview-ready answer

I use class-weighted cross-entropy loss with weights set to the inverse of per-class frequency in the training fold, normalized. With ~30 trials per class the weights are nearly equal, but computing them per fold makes the loss robust to any imbalance that shows up in practice — if a session has fewer trials of one class after noise rejection, the weighting self-adjusts. It's cheap defense against a common failure mode. Class imbalance is also why my reporting metric is macro-F1, not accuracy — the two concerns are related but separate: weighted loss fixes training bias, macro-F1 prevents the evaluation from hiding per-class weakness.

Going deeper (if they push)

  • Effective Number of Samples weighting (Cui et al. 2019): instead of 1/count, uses (1-β) / (1-β^count). Accounts for the fact that the 100th "left" sample adds less new information than the 10th — avoids over-weighting rare classes just because they're rare.
  • Focal loss (Lin et al. 2017): adds a modulating term that down-weights easy-to-classify samples, focusing gradient on hard examples. Developed for dense object detection where most proposals are easy background.
  • Label smoothing: orthogonal to class weighting — softens the target distribution (e.g. 0.9 for correct, 0.05 for others) to prevent the model becoming overconfident. Often combined with class weights in production recipes.
