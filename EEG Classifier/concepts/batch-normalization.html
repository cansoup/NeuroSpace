Concept · Normalization

Batch Normalization

Keeping every layer on the same page as the others shift around.

TL;DR

As the network trains, the distribution of values flowing into each layer keeps shifting, because every layer's weights are updating at once. Batch norm re-centers and re-scales those values to mean 0, variance 1 within each mini-batch. The result: faster training, bigger allowable learning rates, and a small regularization bonus.

The problem it solves

Imagine you're teaching Layer 3 of a network to recognize patterns in the output of Layer 2. Layer 3 learns something useful. Great. Meanwhile, Layer 2's weights are also being updated by backprop — so what Layer 2 outputs next epoch looks different from what it output last epoch. Layer 3 has to relearn. Layer 4, which depends on Layer 3, now has the same problem.

This cascading effect is called internal covariate shift. It's why deep networks used to be so hard to train: you had to tiptoe with tiny learning rates to keep the layers from diverging out of sync. Batch norm solves this by nailing each layer's input distribution to a fixed shape — mean 0, variance 1 — regardless of what upstream weights are doing.

Historical note: the "internal covariate shift" story is the one Ioffe & Szegedy told in their 2015 paper, and it's the intuition most people carry. Later work (Santurkar et al. 2018) showed the real benefit is a smoother loss landscape — batch norm flattens the optimization surface, which is why higher learning rates become safe. Both framings predict the same behavior; if asked, mention either.

How it works

For a mini-batch of activations, BatchNorm does four things per channel: 

1. Compute batch mean:     μ = mean(x)
2. Compute batch variance: σ² = var(x)
3. Normalize:              x̂ = (x - μ) / √(σ² + ε)
4. Scale and shift:        y = γ·x̂ + β      (γ, β are learned per channel)

Steps 1-3 put the data on a standard scale. Step 4 gives the network a way to undo the normalization if it turns out some layer really does want its input scaled differently. γ and β are trainable parameters — the network learns how much normalization each channel actually needs.

Train mode vs eval mode (the gotcha)

During training, batch norm uses the statistics of the current mini-batch. But at inference time, you might be predicting on a single sample — what's the "batch mean" of one sample? (Answer: itself. That's useless.)

So during training, batch norm also tracks running averages of mean and variance across all batches it sees. At inference, it uses those running statistics instead of the current input. This is why PyTorch distinguishes model.train() from model.eval() — they pick different behaviors.

Forgetting model.eval() at inference is the #1 batch norm bug. If you run inference in train mode, each single-sample prediction will be normalized against itself (mean = x, variance = 0), which collapses everything to zero. Predictions become nonsense. load_model() calls model.eval() before returning — this is not decoration, it's critical.

In your project

Both EEGNet blocks apply BatchNorm2d after every convolution (eeg_online_classifier.py:165–188): 

self.block1 = nn.Sequential(
    nn.Conv2d(1, F1, (1, kern_len), ..., bias=False),
    nn.BatchNorm2d(F1),                          # after temporal conv
    nn.Conv2d(F1, F1*D, (n_channels, 1), ..., bias=False),
    nn.BatchNorm2d(F1*D),                        # after spatial conv
    nn.ELU(),
    nn.AvgPool2d((1, 4)),
    nn.Dropout(dropout),
)

Notice bias=False on the convs. That's not a typo — when a conv is followed immediately by batch norm, the bias term is redundant. BatchNorm's β parameter does the same job and is learnable in exactly the same way. Removing the conv bias saves a handful of parameters and avoids a subtle redundancy.

The order Conv → BN → Activation → Pool → Dropout is the EEGNet canonical stack. It's the same order used in the original paper and in countless modern CNNs.

Why batch norm also acts as mild regularization

Each training batch's mean and variance are slightly different from every other batch. This means the same activation gets normalized slightly differently every time it's seen, which injects a tiny amount of noise into training. That noise has the same flavor as dropout's: it prevents the network from latching too hard onto specific activations.

The effect is mild — you still need dropout — but it's the reason networks with batch norm generally need less dropout than networks without it.

Pitfalls

Tiny batch sizes break it. If your batch size is 1 or 2, the per-batch mean and variance are too noisy to be useful statistics. Your batch size of 16 is fine. If memory forced you below ~4, consider GroupNorm or LayerNorm instead.

Sensitive to batch composition. If every batch happens to contain only one class (imagine shuffling broke somehow), the per-channel statistics become class-specific and the model can't generalize. Shuffled, class-balanced batches — which your DataLoader provides — are assumed.

Interview-ready answer

Batch norm normalizes activations to mean 0, variance 1 within each mini-batch, then applies learned scale and shift. It stabilizes training by keeping inter-layer input distributions consistent as all layers' weights update together, which lets you use higher learning rates and converge faster. I apply it after every conv in EEGNet and drop the conv bias term because batch norm's shift parameter already provides it. At inference, PyTorch automatically switches to running statistics when the model is in eval mode.

Going deeper (if they push)

  • LayerNorm: normalizes across features within a single sample instead of across the batch. Standard in Transformers because batch size doesn't interact with the statistic.
  • GroupNorm: splits channels into groups and normalizes each group. A good fallback when batch sizes are very small (object detection, medical imaging).
  • InstanceNorm: normalizes each sample's each channel independently. Popular in style transfer, where batch-level statistics would pollute per-image style.
  • Training-eval drift: if your running statistics don't match your deployment data distribution (e.g. impedance drift between sessions), you can see accuracy drop at inference. This is a known BCI failure mode; calibration or online re-estimation of stats is one fix.
